# 📱 PWA & Offline Strategy

> The app is a Progressive Web App: installable, offline-capable, fast on repeat visits.

## What's already wired

The `vite-plugin-pwa` plugin (see `vite.config.ts`) handles:

- **Web App Manifest** — name, icons, theme color, display mode.
- **Service Worker** generated by Workbox at build time (`dist/sw.js`).
- **Auto-update** strategy — when a new version is deployed, the SW updates on next navigation.
- **App shell precaching** — HTML, JS, CSS, and listed assets are cached on first load.
- **Runtime cache for API** — `NetworkFirst` strategy with a 5s timeout for `/api/*`.

## How it works in production

1. User visits the app. Vite serves `index.html`, which registers the service worker.
2. SW precaches the app shell (JS chunks, CSS, etc.) using the manifest generated by Workbox.
3. On subsequent visits, SW serves the shell from cache → near-instant load.
4. API calls go through `NetworkFirst`: try the network, fall back to the last cached response if offline or slow.

## How it works in development

By default, the PWA is **disabled in dev** (`devOptions.enabled: false` in `vite.config.ts`).

Reason: a service worker caching stale chunks during HMR is a debugging nightmare.

To test PWA behavior locally:

```bash
pnpm build
pnpm preview
```

This serves the production build (with SW) on `http://localhost:4173`.

## Cache strategies, explained

Workbox supports several strategies. We use:

| Strategy               | Where          | Behavior                                                                       |
| :--------------------- | :------------- | :----------------------------------------------------------------------------- |
| `Precache`             | App shell      | Cached at SW install. Always served from cache.                                |
| `NetworkFirst`         | API (`/api/*`) | Try network with 5s timeout. Fall back to cache. Cache for 24h.                |
| `CacheFirst`           | _(future)_     | Serve from cache, only network if missing. Good for images.                    |
| `StaleWhileRevalidate` | _(future)_     | Serve cache immediately, update in background. Great UX for non-critical data. |

When we add user-uploaded images or static reference data, we'll likely add a `CacheFirst` rule for them.

## Deploy checklist

Critical for PWA to work correctly:

- ✅ **HTTPS** — service workers refuse to register on HTTP (except localhost).
- ✅ **Cache headers**:
  - `index.html` → `Cache-Control: no-cache` (so updates propagate).
  - `sw.js` and `workbox-*.js` → `Cache-Control: no-cache`.
  - `manifest.webmanifest` → `Cache-Control: no-cache`.
  - `assets/*.{js,css}` → `Cache-Control: public, max-age=31536000, immutable`.
- ✅ **SPA fallback**: 403/404 → `/index.html`.
- ✅ **PWA icons** in `public/`:
  - `pwa-192x192.png`
  - `pwa-512x512.png` (also used for maskable purpose).
  - `apple-touch-icon.png` (180×180 PNG for iOS).
  - `favicon.ico` and `favicon.svg`.

You'll need to generate these icons before deploying. Tools like [PWA Asset Generator](https://github.com/elegantapp/pwa-asset-generator) or [Real Favicon Generator](https://realfavicongenerator.net) do this from a single source image.

## Going further: offline-first

The current setup is **online-first with offline fallback**. For a true offline-first second-brain experience, future iterations could add:

### 1. IndexedDB for local persistence

Cache the user's items locally so they're available even when the API cache misses. Libraries to consider:

- **`idb`** (~1KB) — thin promise wrapper around IndexedDB. Minimalist.
- **`dexie`** (~25KB) — fuller-featured: queries, transactions, hooks.

Wire-up sketch:

```ts
// src/services/itemsRepo.ts (a future file)
export const itemsRepo = {
  async saveAll(items: Item[]): Promise<void> {
    /* idb.put */
  },
  async getAll(): Promise<Item[]> {
    /* idb.getAll */
  },
  async getById(id: string): Promise<Item | undefined> {
    /* idb.get */
  },
}
```

Then composables read from `itemsRepo` first, sync from `itemsApi` in the background.

### 2. Offline mutation queue

When the user creates or edits an item while offline:

1. Optimistically apply the change to local IndexedDB.
2. Push the mutation to a queue (also in IndexedDB).
3. When the network returns, flush the queue to the backend.
4. Reconcile conflicts (last-write-wins, or surface to the user).

This is real engineering — don't build it before the basic flows work online.

### 3. Background Sync

Browsers support the **Background Sync API** which lets the SW retry failed requests when connectivity returns, even if the tab is closed. Worth adding once a mutation queue exists.

## Testing the PWA

Tools to verify your PWA setup:

- **Chrome DevTools → Application tab** — inspect the SW, manifest, cache storage, IndexedDB.
- **Lighthouse** (DevTools or CLI) — PWA score, manifest checks, offline-ready check.
- **Network tab → Offline checkbox** — simulate going offline.
- **`chrome://serviceworker-internals`** — low-level SW inspection.

## Common pitfalls

| Symptom                                            | Cause                                                                             |
| :------------------------------------------------- | :-------------------------------------------------------------------------------- |
| Users stuck on an old version after deploy         | `index.html` or `sw.js` cached too aggressively at the CDN.                       |
| Service worker registers but nothing is cached     | Build wasn't run with `pnpm build`; SW only generates on build.                   |
| Install prompt never appears                       | Missing icons in `public/`, or HTTPS not enforced.                                |
| API calls return stale data offline                | That's by design (`NetworkFirst` cache fallback). Tune `maxAgeSeconds` if needed. |
| `Cannot find name 'self'` in TS for SW custom code | Add `"WebWorker"` to `lib` in tsconfig for the SW file.                           |
